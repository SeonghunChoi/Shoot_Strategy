# 본 게임 1차 마일스톤 — 버티컬 슬라이스 계획

> 문서 상태: v1.0 (2026-10-26, 확정)
> 짝 문서: `횡스크롤_전략_비행슈팅_기획서.md` (v0.3.1), `횡스크롤_전략_비행슈팅_기술설계.md` (v0.5)
> 앞선 검증: 전투 프로토타입(Q1~Q9, 10-20 종료), 전략 프로토타입(S1~S8·V1~V4, 10-21 종료)

---

## 1. 목적과 위치

### 1.1 무엇을 만드는가

**전략 맵 ↔ 슈팅 전투 한 바퀴가 본 아키텍처 위에서 끝까지 도는 작은 게임**이다. 콘텐츠는 적지만 각 부분은 출시 품질의 구조로 만든다.

- 프로토타입과 달리 **버리는 코드가 아니다**. 기술설계 v0.5의 어셈블리·DI·데이터 파이프라인·세이브·UI 규칙을 모두 따른다
- 프로토타입 코드는 참고만 하고 `Assets/_Game/Code/`로 복사하지 않는다. 검증된 규칙(헥스 연산, 다턴 비행, 자동 정산 라운드)은 새 구조에 맞춰 다시 쓴다
- 콘텐츠 폭은 좁게, 흐름은 끝까지: 기체 3종·지형 1종·보스 1·미션 2종으로 "이륙 → 비행 → 교전(직접/자동) → 결과 적용 → 적 턴 → 저장/불러오기"를 반복할 수 있어야 한다

### 1.2 왜 이 범위인가

| 이유 | 내용 |
|---|---|
| 아키텍처 검증 | 문서로만 정한 경계(Combat은 Core를 모름, 교전 계약, 동기 상태 머신, 언제든 저장)를 실제 코드로 한 번 통과시킨다. 구조 문제는 콘텐츠가 적을 때 고쳐야 싸다 |
| 남은 기획 위험 | 다턴 비행에서 직접 슈팅 비중이 줄어드는 위험(기획서 12장)은 전략 프로토타입이 자동 정산만 써서 드러나지 않았다. 직접 전투와 전략이 연결돼야 측정할 수 있다 |
| 제작 속도 실측 | 기체 1대·청크 1개·패널 1개를 만드는 데 실제로 얼마나 걸리는지 알아야 전체 콘텐츠 규모를 정할 수 있다 |

### 1.3 일정과 브랜치

- 기간: **2026-10-26 ~ 2027-01-17 (12주)**, 마지막 1주는 예비
- 프로토타입처럼 기간이 끝나면 결과가 애매해도 판단을 내리고 종료한다. 밀리면 3.3의 "줄일 순서"대로 줄인다
- 브랜치: `main`이 본 게임 기준. 단계마다 `feature/m1-<단계>` 브랜치를 따서 끝나면 `main`에 병합 (기술설계 §2.10.6). 프로토타입 브랜치와 `Assets/Prototype/`은 병합하지 않는다

## 3. 범위

### 3.1 포함 — 게임 내용

| 영역 | 내용 |
|---|---|
| 전략 맵 | 1구역, 도시판 크기 전후(전략 프로토타입 기준). 지형 5종 표시, 자원 타일 소수 |
| 세력 | 플레이어 + 적 세력 1개 |
| 거점 | 아군 거점 2개, 적 거점 2개(그중 하나에 보스). 시설은 격납고·활주로·정비소 정도로 축소 |
| 편대·기체 | 편대 2개, 편대당 최대 3기. 기체 3종: 제공기·공격기·폭격기 (전투 프로토타입과 같은 역할 구성) |
| 파일럿 | 일반 파일럿만. 피로·탈출(포로 없음) |
| 비행 | 다턴 비행, 연료, 귀환·자동 귀환. 드롭탱크·급유기는 제외 |
| 시야 | 거점 시야 + 미확인 접촉 "?" (전략 프로토타입 "가장 재미있었던 결정") |
| 교전 | 미션 2종(부대 공격, 거점 공격) + 적 선공 교전 + 거점 자동 요격(자동 정산만). 교전마다 직접/자동 선택 |
| 자동 정산 | 라운드제 리졸버, 최소 1라운드 교전 규칙, 불리 계수 (기술설계 5.4) |
| 적 AI | 태세 2종(확장·공세) + 행동 점수화 단순판, 동시 공세 2방향 (S1 피드백) |
| 경제 | 자금, 기본 수입, 거점 유지비, 수리비. 상점·연구 없음 |
| 전투 | 스크롤·스로틀(모드 B), 기체 전환(탭·링), 기관포·유도 미사일·폭탄, 공중 잡몹 3종, 대공포·지상 목표, 지형 1종(산악 + 평지 구간), 선회 구역 + 고정형 보스 1(지상 요새), 레이더 세로 띠 + 진입 예고 + 지형 예고 |
| 승패 | 승리: 적 보스 거점 함락 / 패배: 아군 거점 전부 상실 |

### 3.2 포함 — 기술 (기술설계 v0.5)

| 영역 | 내용 |
|---|---|
| 구조 | 7개 어셈블리 + DevTools·Editor·Tests, asmdef 참조표 그대로. VContainer 루트·자식 스코프, Boot/Strategy/Combat 씬 |
| Core | 상태(`State/`)·규칙·턴 상태 머신·커맨드 결과와 도메인 사건·시드 난수. `DotNet/` 테스트·시뮬레이션 |
| 계약 | `SortieContext`/`SortieResult` 교전 1건 단위, 직접/자동 같은 적용 경로 |
| 데이터 | xlsx 임포터 **최소판** — 시트: Aircraft, Weapons, Enemies, Waves, Terrain(청크 메타), Localization. 검증기(ID 형식·참조 누락) |
| 세이브 | MessagePack 문자열 키, 수동 저장 + 자동 저장(턴 시작·교전 직전·교전 후), JSON 덤프. 스키마 버전 필드만 (마이그레이션은 아직 불필요) |
| 설정 | 플레이어 설정 파일 (패드 배치, 링 슬로모션, 순항 복귀, 음량, 언어) |
| UI | UI Toolkit: 상단 바, 편대 명령, 격납고(축소판), 브리핑, 디브리핑, 적 턴 요약, 전투 HUD, 일시정지·설정. 1280×800 기준, 패드 탐색 |
| 로컬라이제이션 | 영어·한국어 두 언어를 처음부터. 한글 폰트 동적 아틀라스 |
| 렌더링 | 툰 셰이더 + 외곽선 + 팔레트 세력 도장(2행) + 디칼(UV2). 전략 맵 병합 메시 + 오버레이 텍스처 |
| 전투 기술 | 탄 NativeArray + Burst Job + `RenderMeshInstanced`, 지형 높이 곡선(판정·메시·예고 공용), 양방향 진행 |
| 개발 도구 | 플레이 로그(교전·전투 사건·턴), 튜닝 오버레이(xlsx 변경분 내보내기), 헤드리스 시뮬레이션 |
| 빌드 | Jenkins: `dotnet test` → 데이터 임포트·검증 → Addressables → Windows IL2CPP. 테스터 빌드 zip |
| Addressables | 공용·전략·기체·청크·적·궤적·보스 그룹 골격 (원격 카탈로그 없음) |

### 3.3 제외

연구·역설계, 부품 개조, 하드포인트 무장 교체 UI(장착은 고정), 상점, 라이벌 에이스, 네임드 파일럿·포로, 지상군, 상부 신뢰도·지시, 급유기·드롭탱크, 초토화, 구역 개방·스토리, 헥스 맵 에디터(맵은 xlsx 또는 임시 SO로 저작), 청크 자동 조립 생성기(고정 시퀀스만), 배경 레이어 편대, 손상 그을음·파괴 연출 고급화, Steamworks, 세이브 마이그레이션, 콘솔.

**일정이 밀릴 때 줄일 순서** (위부터):
1. 적 태세 2종 → 1종 (공세만)
2. 기체 3종 중 2종은 프록시 모델(기본 도형 + 툰 셰이더)로 — 정식 모델 1대는 유지 (M5)
3. 격납고 패널 → 편성 순서 변경만
4. 미션 2종 → 부대 공격 1종 (적 선공·보스는 유지 — M1·M2의 핵심)

## 7. 종료 조건과 결과 반영

**종료 조건** — 아래가 모두 충족되거나 기간이 끝나면 종료한다.
- 6.2 자동 확인 전부 녹색
- 테스터가 패드만으로 새 게임 → 10턴 이상 → 승리 또는 패배까지 진행 가능
- M1~M8에 판단이 나옴

**결과 반영**
- M1·M2·M3 → 기획서 3장 출격 규칙·12장, 기술설계 5.3 정책
- M5·M6 → 기술설계 7.4 폴리곤 예산, 6.2 탄 수 상한, 9장
- M7·M8 → 기획서 11장, 기술설계 2.8·6.7
- 단계별 실제 소요 기간 → 2차 마일스톤 계획(콘텐츠 확장 순서와 규모)

**이 마일스톤의 코드는 남는다.** 판단 결과로 바뀌는 것은 규칙 수치와 정책 값이어야 하고, 구조를 고쳐야 한다면 그것 자체가 M4의 답이다.
