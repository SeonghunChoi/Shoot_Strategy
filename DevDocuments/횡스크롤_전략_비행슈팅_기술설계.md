## 2. 전체 아키텍처

### 2.1 어셈블리

| 어셈블리 | 역할 | 의존 |
|---|---|---|
| Game.Core | 순수 C# 도메인: 월드, 헥스 맵, 거점·시설·자원 타일, 편대·기체·파일럿, 비행(연료·급유기), 지상군, 세력, 시야·미확인 접촉, 경제, 턴 처리, 커맨드, 이벤트, 자동 정산 리졸버, 적 AI | 없음 (UnityEngine 미참조) |
| Game.Contracts | 레이어 간 공유 타입: 출격 컨텍스트·결과, 정적 데이터 정의 레코드, 메시지 구조체 | 없음 |
| Game.Data | ScriptableObject 저작 데이터, xlsx 임포터(에디터), 정의 레코드 변환 | Contracts |
| Game.Strategy | 전략 맵 뷰, 헥스 입력, 운영 패널 UI | Core, Contracts |
| Game.Combat | 전투 씬 전체 (기체, 탄 Job, 청크 생성, 보스, HUD, 결과 기록기) | Contracts만 |
| Game.Infra | 세이브/로드, Addressables 로딩, 입력·플랫폼 추상화, 씬 전환 | Core, Contracts |
| Game.App | 부트스트랩, 조립(composition root), 턴-전투 오케스트레이션 | 전부 |

**핵심 규칙**
- Combat은 Core를 모른다. 교전 컨텍스트를 받고 결과를 돌려주는 것만 안다 → 전투 씬 단독 테스트 가능, 전략 규칙 변경이 전투 코드에 파급되지 않음. 연료·맵 위치·드롭탱크·급유기 같은 비행 규칙은 Combat에 들어가지 않는다
- Core의 외부 참조는 **MessagePack(NuGet 코어)만** 허용한다 (세이브 포매터 소스 생성, 3.4). R3 미참조(상태를 순수 데이터로 유지, 2.4), UniTask 금지(Unity 플레이어 루프 의존), MessagePipe 금지(DI 등록 전제를 Core에 들이지 않음). Core는 Unity 없이 테스트 러너와 .NET 프로젝트(8.5)에서 동작해야 한다
- Contracts의 외부 참조도 **MessagePack만**. 세이브에 대기 중인 교전(`SortieContext`)과 ID 타입이 들어가는데 이 타입들이 Contracts에 있기 때문이다. Combat은 Contracts를 통해 MessagePack을 간접 참조하지만 쓰지는 않는다. Core·Contracts는 Unity와 .NET 프로젝트 양쪽에서 컴파일되므로 C# 언어 버전을 Unity 기준(C# 9)으로 맞춘다. `record`·`init`을 쓰려면 `System.Runtime.CompilerServices.IsExternalInit` 보조 정의를 Contracts에 하나 둔다

### 2.2 씬 구성

| 씬 | 로드 방식 | 내용 |
|---|---|---|
| Boot | 상주 | App, Infra, 전역 서비스, 루트 DI 스코프 |
| Strategy | 추가 로드 | 전략 맵, UI, Strategy DI 스코프 |
| Combat | 추가 로드 (Strategy와 교체) | 전투, 출격 컨텍스트를 주입받는 Combat DI 스코프 |

전략 상태는 전부 Core 메모리에 있으므로, 전투 중 Strategy 씬을 내려 메모리를 확보할 수 있다.

### 2.3 DI (VContainer)

- Boot의 루트 `LifetimeScope` 아래 Strategy·Combat을 씬별 자식 스코프로 구성
- Combat 스코프는 생성 시 `SortieContext`를 파라미터로 주입받음
- Core 서비스는 루트 스코프에 등록하되, Core 코드 자체는 VContainer를 참조하지 않음 (생성자 주입만 사용)
- MessagePipe는 MessagePipe.VContainer 통합으로 루트 스코프에 등록하고, 메시지 타입별 브로커도 루트에서 등록 → Strategy·Combat 자식 스코프에서 `IPublisher<T>` / `ISubscriber<T>` 주입 (용도는 2.4)

### 2.4 상태·이벤트 전달 (R3 / MessagePipe)

UI와 게임 사이에 오가는 정보를 세 종류로 나누고, 종류별로 도구를 정한다.

| 종류 | 예시 | 도구 | 이유 |
|---|---|---|---|
| 상태 | 체력, 선택된 타일, 자금, 신뢰도, 파일럿 피로 | R3 `ReactiveProperty` | UI가 필요한 것은 "지금의 값". 구독으로 자동 갱신 |
| 출처를 아는 사건 | HUD가 조종 중인 기체의 피격 연출 | R3 Observable (발생 대상이 노출) | 받는 쪽이 이미 대상을 알고 있으므로 대상에 직접 구독 |
| 출처를 모르는 사건 | 효과 매니저, 사운드 매니저, 전투 결과 기록기 | MessagePipe (VContainer 주입 `IPublisher<T>` / `ISubscriber<T>`) | 중앙 수신자가 "누가"를 몰라도 "무슨 일"을 받아야 함 |

**판단 규칙**: 값이면 R3, 출처를 모르는 곳에서 오는 소식이면 MessagePipe. 대부분의 흐름(상태 바인딩)은 R3가 맡고, MessagePipe는 중앙 집중 수신자라는 좁은 용도로만 쓴다. 이 표는 **Core 바깥**(Strategy·Combat·App)의 규칙이다.

**Core에서 바깥으로 — 커맨드 결과와 도메인 사건**
- Core는 R3도 MessagePipe도 쓰지 않는다. 월드 상태는 순수 데이터 클래스(3.3)이고, 상태를 바꾸는 유일한 길은 커맨드다
- 커맨드 처리(턴 처리기 진행 포함)는 **결과 + 도메인 사건 목록**을 돌려준다. 사건은 Contracts의 불변 레코드 (예: 편대 도착, 자금 변동, 거점 등급 상승, 교전 대기). 이동 기록(`MoveTrace`, 2.5)과 적 턴 요약(기획서 11.3)도 같은 사건 목록에서 만든다
- Strategy 프레젠터는 사건 목록을 받아 자기가 가진 R3 `ReactiveProperty`를 갱신한다 (값의 원본은 Core 상태, `ReactiveProperty`는 그 사본). 어떤 값이 바뀌었는지 사건만으로 알기 어려운 패널은 커맨드 후 상태에서 다시 읽는다
- 출처를 모르는 수신자(사운드·효과·플레이 로그)에게 알려야 할 사건은 App 레이어가 사건 목록을 받아 MessagePipe로 중계한다

**운영 규칙**
- 메시지는 구조체로 정의한다 (전투 중 잦은 사건을 할당 없이 전달)
- 탄 충돌은 Burst Job에서 판정되므로, Job 완료 후 메인 스레드에서 판정 결과를 모아 발행한다
- 메시지 타입은 Contracts에 둔다 (Combat은 Contracts만 참조)
- 새 메시지 타입을 만들기 전에 "받는 쪽이 출처를 정말 모르는가?"를 확인한다. 안다면 R3로 충분하다

### 2.5 턴 처리

- Core의 턴 처리기는 **async 없는 동기 상태 머신**
- 단계: **플레이어 턴**(운영·명령·편대 비행을 자유 순서로) → 턴 종료 처리(비행 편대 연료·피로, 급유기 떠남, 수입·지출) → 아군 지상군 AI → **적 턴**(세력·부대 단위로 한 걸음씩) → 다음 턴
- v0.3의 "출격 계획 확정 → 순차 실행" 단계는 없어졌다. 편대 비행 명령은 커맨드 하나로 즉시 처리되고(이동 → 도착 칸 판정), 그 결과가 다음 명령의 전제가 된다. 커맨드는 결과와 도메인 사건 목록을 돌려준다 (2.4)
- **교전 대기 상태**: 커맨드 처리나 적 턴 진행 중 교전이 생기면 턴 처리기는 `PendingEngagement`(교전 컨텍스트 1건)를 들고 멈춘다. App이 직접/자동을 정해 결과를 제출하면 결과를 적용하고 멈춘 지점부터 이어 간다
  - 플레이어 턴: 비행 명령이 적 칸에 도착 → 교전 대기 → 결과 적용 → 다시 명령 대기
  - 적 턴: 적 부대의 이동 한 걸음마다 접촉(비행 편대 맞닿음)·거점 공격(자동 요격)을 판정. 교전이 생기면 적 턴 커서(세력 인덱스, 부대 인덱스, 남은 이동력)를 상태에 남기고 멈춘다
- 전투 씬 로드와 대기 같은 비동기 흐름은 App 레이어가 UniTask로 조율
- 상태 머신의 현재 위치(단계, 대기 중인 교전, 적 턴 커서)가 데이터이므로 어느 시점에서든 직렬화 가능 → "언제든 저장"의 전제
- **이동 기록**: 편대 비행·적 이동·지상군 이동은 칸 단위 이동 기록(`MoveTrace`: 주체, 경로, 칸마다 보였는지, 도착 사건)으로 상태에 남는다. Strategy 뷰는 이를 받아 재생할 뿐 결과를 계산하지 않는다 (재생 중 건너뛰기는 뷰만의 일). 기록은 턴이 넘어가면 비운다

### 2.6 결정론

- 모든 무작위성은 Core 전용 시드 난수로 처리
- 같은 세이브 + 같은 커맨드 = 같은 결과 → 헤드리스 밸런싱 시뮬레이션, 버그 재현, 자동 정산 세이브 스컴 방지
- **조회는 난수를 쓰지 않는다**: UI가 언제 몇 번 묻는지에 따라 결과가 바뀌면 안 되므로, 조회성 무작위(미확인 접촉의 위치 오차 등)는 시드·대상 ID·턴으로 만든 해시로 고정값을 낸다. 난수 스트림은 상태를 바꾸는 규칙만 소비한다

### 2.7 프로젝트 폴더 구조

**원칙**
- 프로젝트 에셋은 `Assets/_Game/` 하나로 묶는다. 밑줄로 목록 최상단에 고정되고, 서드파티가 `Assets/` 바로 아래 만드는 폴더와 섞이지 않는다
- `_Game` 아래 최상위는 **용도별 7개로 고정**. 콘텐츠가 늘어나도 최상위는 늘지 않는다
- 최상위 아래 3단계 이내를 목표로 한다
- 여러 파일로 이뤄진 콘텐츠(기체·보스 등)는 **ID 폴더 하나에 모은다** (모델·프리팹·디칼을 함께)
- Unity가 직접 다룰 필요 없는 원본은 `Assets` 밖에 둔다. 데이터 원본(`.xlsx`)은 저장소의 `SourceAssets/`, 제작 원본(`.blend`·레이어 텍스처·오디오 프로젝트)은 저장소 밖 동기화 폴더

**저장소 루트**

```

├─ Packages/
├─ ProjectSettings/
├─ DotNet/                       Unity 밖 .NET 프로젝트 (8.5)
│  ├─ Game.DotNet.slnx
│  ├─ Game.Core/Game.Core.csproj Assets/_Game/Code/Core·Contracts 소스를 링크로 포함 (복사 아님)
│  ├─ Game.Core.Tests/           `dotnet test`

│  └─ Tables/                    .xlsx 원본 (LFS), Snapshots/ (임포트 시 생성되는 JSON 텍스트 스냅샷)

```

- Git에는 **내보낸 결과**(FBX, PNG, WAV/OGG)만 들어간다. 원본 루트 위치는 사람마다·머신마다 다를 수 있으므로 코드·도구가 경로를 가정하지 않는다
- 이력·백업은 클라우드 드라이브의 버전 기록에 맡긴다. 큰 수정 전에는 `<ID>_v<번호>.blend`로 수동 스냅샷
- 빌드 머신은 원본 루트가 필요 없다 (Assets만으로 빌드)

**Git 설정**
- `.gitignore`: Unity 템플릿의 `*.csproj` 규칙이 `DotNet/`까지 막으므로 `!/DotNet/**/*.csproj` 예외를 둔다. `DotNet/**/bin/`·`obj/`는 제외. Unity가 루트에 만드는 `/*.slnx`·`/*.csproj`는 제외 (현재 `Shoot_Strategy.slnx`가 커밋돼 있음 → 추적 해제)
- `.gitattributes`: `SourceAssets/**/*.xlsx`와 FBX·텍스처·오디오를 LFS로 (8.1). `.blend`는 저장소에 들어오지 않으므로 `.gitignore`에도 `*.blend`를 넣어 실수로 커밋되는 것을 막는다

`.blend`가 Assets 안에 있으면 Unity가 블렌더를 호출해 임포트하려 하므로 블렌더가 없는 빌드 머신에서 문제가 된다. 블렌더에서 FBX로 내보낸 결과만 `Assets`에 둔다.

|---|---|
| `Code` | `Scripts`는 Unity가 특별한 의미를 두지 않는 관례적 이름으로, 게임오브젝트에 붙이는 MonoBehaviour라는 인상이 강하다. 이 폴더의 가장 큰 덩어리인 Core·Contracts는 Unity 비의존 순수 C# 라이브러리이고, asmdef 정의·에디터 도구·테스트 어셈블리까지 함께 담기므로 "코드베이스 전체"라는 의미로 `Code`로 명명 |

| `Data/Generated` | 임포터가 덮어쓰는 산출물을 사람이 만드는 SO와 분리해 수정 금지 영역을 명확히 하고, 검증 도구의 대상 범위를 한정 |
| `Rendering` | 셰이더·팔레트는 특정 콘텐츠가 아니라 전 콘텐츠의 공유 기반. 특히 팔레트 행 교체로 세력 도장을 바꾸므로 기체 폴더에 두면 안 됨 |
| `Scenes/Sandbox` | Combat이 Core를 모르는 구조를 활용한 전투 단독 테스트 씬, 셰이더 실험 씬 |
| `DotNet` | Core 테스트·시뮬레이션을 에디터와 무관하게 돌리기 위한 것. `Assets` 밖이라 Unity가 임포트하지 않고, 소스는 `Assets/_Game/Code/`에 한 벌만 존재 |

### 2.8 UI 기술 — UI Toolkit

- 전략 맵 패널(기획서 11.2의 7개), 메뉴, 브리핑·디브리핑, 전투 HUD를 모두 **UI Toolkit**으로 만든다. uGUI는 쓰지 않는다 (두 체계를 유지하지 않기 위해)
- 레이아웃은 UXML, 스타일은 USS. 공용 스타일시트(색·글꼴·간격 토큰)를 하나 두고 패널은 그것만 참조 → 프로토타입에서 지적된 UI 사용 편의성(기획서 11.1)을 화면 단위가 아니라 스타일 단위로 고친다
- 값 표시는 Unity 6 런타임 데이터 바인딩으로 프레젠터의 `ReactiveProperty`에 연결 (프레젠터가 바인딩 소스, 2.4)
- 패드 탐색: Input System UI 입력 모듈 + UI Toolkit 포커스 탐색. 패널 탭 전환(숄더)·확인 한 버튼(기획서 11.4)은 패널 공통 컨트롤러에서 처리
- 텍스트는 Localization 패키지의 UI Toolkit 바인딩으로 키(`AC_F16.name`)에 연결
- 직접 그려야 하는 요소(전투 레이더 세로 띠, 진입 예고 화살표, 지형 예고)는 `VisualElement` 커스텀 그리기(`Painter2D`/메시 생성)로 HUD 안에 둔다
- 전략 맵 자체(헥스·오버레이·유닛 표식)는 UI가 아니라 월드 렌더링 (4.4)
- 저작 위치: `Content/UI/` (UXML·USS·아이콘)
- **Steam Deck 기준 (1장)**: PanelSettings 기준 해상도 1280×800, 화면 크기에 맞춰 확대. 본문 글자는 Deck 화면에서 읽히는 크기를 최소값으로 토큰에 고정하고, 패널 밀도는 그 크기에서 설계한다. 마우스 호버에만 의존하는 정보 표시 금지 (패드 포커스로도 같은 정보)
- 한국어 글자가 영어보다 짧고 영어가 길다 → 레이아웃은 영어 기준 폭으로 검증 (3.2)

### 2.9 개발 도구 — 플레이 로그와 튜닝 오버레이

두 프로토타입의 판정은 대부분 플레이 로그(`runs.csv`/`events.csv`, 전략 플레이 기록)와 튜닝값 내보내기에서 나왔다. 본 게임에도 처음부터 둔다.

| 도구 | 위치 | 내용 |
|---|---|---|
| 플레이 로그 | Infra (`PlayLog`) | 교전 단위(발생 경위·미션·직접/자동·소요 시간·결과, 5.3) + 전투 사건 단위(격추·피해·지형 충돌·전환·선회, 위치 포함) + 턴 단위(자금·수지·신뢰도). App이 Core 도메인 사건과 Combat 메시지를 MessagePipe로 받아 기록. CSV, 로컬 전용(Git 제외) |
| 튜닝 오버레이 | 개발 빌드 전용 어셈블리 (`Game.DevTools`, 릴리스 빌드에서 제외) | 실행 중 정의 레코드 값(스크롤 속도, 무방비 시간, 선회 시간 등)을 덮어쓰는 슬라이더. 바꾼 값은 **xlsx에 옮길 변경분**(시트·ID·열·값)으로 내보낸다. 원본은 언제나 xlsx (3.1) |
| 헤드리스 시뮬레이션 | `DotNet/Game.Sim` (8.5) | 세력 AI끼리 N턴, 경제·파산·교전 빈도 집계 |

- 튜닝 오버레이는 정의 레지스트리의 값을 런타임에서만 바꾼다. Core의 결정론에는 영향 없음 (같은 정의 + 같은 세이브 + 같은 커맨드 = 같은 결과)
- 오버레이 UI는 개발 전용이므로 IMGUI 허용 (2.8의 UI Toolkit 규칙 예외)

### 2.10 네이밍 규칙

#### 2.10.1 콘텐츠 ID

- 형식: `접두사_본문`, 대문자·숫자·`_`만. 검증기 정규식 `^[A-Z]{2,5}_[A-Z0-9_]+$` (3.1)
- 본문은 실제 명칭에서 기호를 뺀다 (`F-16` → `AC_F16`). 기체는 **참고한 실기체 이름**으로 ID를 만든다 — ID는 플레이어에게 보이지 않고, 화면 이름(가상 명칭)은 로컬라이제이션 값이라 바뀌어도 ID는 그대로다 (1장)
- **한 번 정한 ID는 바꾸지 않는다** — 세이브(3.4)와 로컬라이제이션 키가 참조한다

| 접두사 | 대상 | 접두사 | 대상 |
|---|---|---|---|
| `AC_` | 기체 | `EN_` | 적 기체·잡몹 |
| `WPN_` | 무장 | `BOSS_` | 보스 |
| `PRT_` | 부품 | `RIV_` | 라이벌 에이스 |
| `FAC_` | 시설 | `FCT_` | 세력 |
| `BASE_` | 고유 거점 | `GND_` | 지상군 |
| `PLT_` | 네임드 파일럿 | `RSH_` | 연구 |
| `CHK_` | 청크 (`CHK_MTN_03`) | `ENV_` | 환경 프로필 (`ENV_MTN`) |
| `SPL_` | 적 궤적 (`SPL_DIVE_L`) | `WAVE_` | 웨이브 |
| `EVT_` | 스토리 이벤트 | `UI_` | UI 문자열 묶음 (`UI_HANGAR`) |

- 지형 코드 3글자: `PLN` 평지, `MTN` 산악, `SEA` 해상, `CST` 해안, `DST` 사막
- **로컬라이제이션 키** = `<ID>.<필드>`, 필드는 소문자 (`AC_F16.name`, `AC_F16.desc`, `UI_HANGAR.title`). UI 문자열도 같은 형식이라 규칙이 하나다 (3.2)
- **Addressables 주소** = ID 그대로. 라벨은 그룹 이름 소문자 (`aircraft`, `chunks`) (8.2)

#### 2.10.2 에셋 파일

- ID가 있는 콘텐츠: **파일명 = ID**, 변형은 `_역할` (`AC_F16.fbx`, `AC_F16.prefab`, `AC_F16_Decal.png`)
- 공용 에셋(셰이더·머티리얼·팔레트 등): PascalCase (`ToonLit.shader`, `ToonLit.mat`, `FactionPalette.png`)
- `M_`·`T_` 같은 **타입 접두사는 쓰지 않는다**. 타입은 폴더와 확장자가 말하고, 대문자 접두사는 콘텐츠 ID 전용
- 셰이더 경로: `Game/<분류>/<이름>` (`Game/Toon/Lit`)
- 씬: `Boot`, `Strategy`, `Combat`, `CombatSandbox`, `ShaderLab`
- SO 에셋: 연결 SO는 `<ID>.asset`, 임포터 산출물은 `Generated/<시트>.asset`

#### 2.10.3 블렌더·FBX 내부 오브젝트

| 이름 | 용도 |
|---|---|
| 루트 = ID | `AC_F16` |
| `HP_<L\|R\|C><번호>` | 하드포인트. 안쪽부터 1 (`HP_L1`, `HP_C`) (7.3) |
| `MZ_<번호>` | 기관포 총구 |
| `FX_<역할>` | 이펙트 지점 (`FX_Exhaust`, `FX_Smoke`) |
| `PT_<부위>` | 보스 부위. xlsx 부위 ID와 짝 (`PT_Turret1`) (6.5) |

#### 2.10.4 xlsx

- 파일은 도메인별 (`Aircraft.xlsx`, `Facilities.xlsx`, `Waves.xlsx` …)
- 시트 이름 = 정의 레코드 이름에서 `Def`를 뺀 것 (`AircraftDef` → `Aircraft`)
- 열 이름 = 레코드 필드 이름 그대로(PascalCase). 첫 열은 `Id`
- 머리글이 `#`으로 시작하는 열은 메모 (임포터가 무시)
- 로컬라이제이션 시트 열: `Key`, 로캘 코드(`ko`, `en`, `ja` …)
- 열거형 값은 이름으로 적는다 (`Fighter`). 오타는 검증기가 잡는다

#### 2.10.5 C# 코드

**기본 스타일** (프로토타입 계승)
- 파일 하나에 public 타입 하나, 파일명 = 타입명
- 네임스페이스 = 어셈블리 이름 + 첫 단계 하위 폴더 (`Game.Core.Rules`). 그보다 깊은 폴더는 반영하지 않는다
- private 필드 `_camelCase`, 상수·`static readonly`는 PascalCase
- `private` 키워드 생략, 클래스는 기본 `sealed`
- bool은 `Is`/`Has`/`Can`, 비동기 메서드는 `XxxAsync`

**역할별 이름**

| 역할 | 규칙 | 예 |
|---|---|---|
| 정의 레코드 / 정의 ID | `XxxDef` / `XxxDefId` (문자열 래퍼) | `AircraftDef`, `AircraftDefId("AC_F16")` |
| 인스턴스 ID | `XxxId` (정수 래퍼) | `AircraftId` = 보유 기체 1기 |
| Core 상태 | 접미사 없는 도메인 명사, public 필드 PascalCase | `World`, `Squadron`, `Aircraft` |
| 무상태 규칙 서비스 | `XxxRules` | `FlightRules`, `EconomyRules` |
| 커맨드 | `XxxCommand` (record) | `FlySquadronCommand` |
| 도메인 사건 | 과거형, 접미사 없음 | `SquadronLanded`, `FundsChanged` |
| MessagePipe 메시지 | `XxxMessage` (struct) | `EnemyDestroyedMessage` |
| 연결 SO 클래스 | `XxxAsset` | `AircraftAsset` |
| 프레젠터 / UI 컨트롤러 / 뷰 | `XxxPresenter` / `XxxPanel` (UXML과 같은 이름) / `XxxView` (MonoBehaviour) | `HangarPresenter`, `HangarPanel` |
| DI 스코프 | `XxxLifetimeScope` | `CombatLifetimeScope` |
| Job | `XxxJob` (struct) | `BulletMoveJob` |
| R3 | 값은 명사, 스트림은 `OnXxx` | `Funds`, `OnHit` |
| 테스트 | 클래스 `<대상>Tests`, 메서드 `Subject_Behavior` | `Jettison_DropsRemainingTankFuel` |

- 정의 ID와 인스턴스 ID를 타입으로 나눠 세이브에서 둘이 섞이는 실수를 컴파일 단계에서 막는다 (프로토타입의 `AircraftType` 열거형 / `Aircraft.Id` 정수에 해당)
- 도메인 사건은 접미사 없이, MessagePipe 메시지만 `Message` — 메시지는 드물게 만드는 것이므로(2.4) 이름에서 드러나게
- **세이브 호환**: 상태에 들어가는 열거형은 값을 명시하고 뒤에만 추가한다 (MessagePack은 열거형을 정수로 저장 → 순서를 바꾸면 기존 세이브가 깨짐). 문자열 `[Key]`(3.3)는 필드 이름을 바꿔도 유지한다

## 3. 데이터 설계

### 3.1 정적 데이터 파이프라인

| 단계 | 내용 |
|---|---|
| 저작 | 수치·표 데이터는 로컬 Excel(.xlsx, `SourceAssets/Tables/`에 커밋). 에셋 연결은 ScriptableObject (`Data/Authored/`) |
| 연결 키 | 문자열 ID (예: `AC_F16`, `FAC_HANGAR`, 접두사·형식은 2.10.1). 시트 행과 SO가 같은 ID로 짝을 이룸 |
| 에셋 참조 | SO에 Addressables `AssetReference`. Core와 시트는 에셋을 모르고 ID만 다룸 |
| 임포트 | 에디터 전용 xlsx 리더로 읽어 정의 데이터 에셋 생성·갱신 (`Data/Generated/`) |
| diff 보완 | 임포트 시 시트 내용을 텍스트(JSON)로도 내보내 함께 커밋 → 밸런스 변경 이력 비교 |
| 검증 | ID 참조 누락, 값 범위, 열거형 오타, SO 짝 누락 검사. 실패 시 빌드 차단 |
| 런타임 | Data 레이어가 시트 데이터 + SO를 Contracts의 불변 정의 레코드로 변환 → 정의 레지스트리로 Core에 주입 |

**xlsx 시트 구성 (예정)**
기체, 부품, 무장, 하드포인트 장착 규칙, 시설(등급별 효과), 거점 등급표, 지상군, 미션, 적 단계, 웨이브, 지상 목표 배치, 세력(AI 가중치·태세 문턱값), 로컬라이제이션 원문

### 3.2 로컬라이제이션

- Unity Localization 패키지
- 키는 ID에서 규칙으로 파생 (예: `AC_F16.name`, `AC_F16.desc`, UI는 `UI_HANGAR.title` — 2.10.1)
- 원문은 xlsx 별도 시트에서 저작, 임포터가 String Table Collection에 반영 → 저작 위치는 xlsx 하나로 유지
- 출시 언어: **영어(`en`), 한국어(`ko`)**. 원문은 한국어로 쓰고 영어 열을 채운다. 영어가 비어 있는 키는 검증기가 경고 (출시 빌드에서는 실패)
- 개발 초기부터 두 언어를 함께 넣는다 → 레이아웃이 한 언어에 맞춰 굳지 않게
- 폰트: 한글을 포함하는 폰트 하나(라틴 포함)를 기본으로 하는 UI Toolkit 폰트 에셋. 한글 글리프가 많으므로 동적 아틀라스로 시작하고, 출시 전 사용 글자 집합으로 정적 아틀라스 생성을 검토
- 기체 화면 이름은 가상 명칭 (1장). `AC_F16.name`의 값이 가상 이름이다

### 3.3 런타임 상태

- **상태와 규칙 분리**: 월드 상태는 로직 없는 순수 데이터 클래스, 규칙은 상태를 받아 변경하는 무상태 서비스 (ECS의 컴포넌트·시스템 분리와 같은 사고방식)
- 상태 자체를 직렬화하므로 별도 세이브 DTO 불필요
- 상태 클래스에는 `ReactiveProperty`·이벤트·델리게이트를 두지 않는다. 필드는 기본형, 문자열 ID, 상태 클래스, 그 컬렉션만 (UI 갱신 경로는 2.4)
- 상태 클래스에 `[MessagePackObject]`와 문자열 `[Key("...")]`를 명시한다. 키는 필드 이름을 바꿔도 유지하는 저장 이름이다

### 3.4 세이브

| 구성 | 내용 |
|---|---|
| 월드 상태 | 도메인 상태 전체 (정의 데이터는 ID로만 참조) |
| 턴 상태 | 현재 단계, 대기 중인 교전(컨텍스트 + 발생 경위), 적 턴 커서, 이번 턴 이동 기록 |
| 난수 상태 | Core 난수 시드와 현재 상태 |
| 메타 | 세이브 스키마 버전, 정의 데이터 버전 해시, 플레이 시간 |

- 포맷: **MessagePack 하나**, 문자열 키(맵 모드). 정수 키보다 크지만 싱글플레이 전략 세이브라 차이는 무시할 수준이고, 필드 추가·순서 변경에 강하다
- 포매터는 MessagePack v3 소스 생성기가 Core 안에 만든다 → IL2CPP에서 리플렉션 없이 동작. Core가 MessagePack을 참조하는 이유 (2.1)
- 개발 중 읽기용: `MessagePackSerializer.ConvertToJson`으로 사람이 읽는 JSON 덤프를 세이브 옆에 남긴다 (개발 빌드 옵션). JSON은 덤프일 뿐 로드 경로가 아니다
- 스키마 버전별 마이그레이션 단계로 업데이트 후 호환 유지
- 정의 데이터 해시 불일치 시 "밸런스 변경 후 세이브" 경고
- 저장 시점: 수동은 전투 중 제외 언제든, 자동은 턴 시작·각 교전 직전·각 교전 결과 적용 직후 (교전 직전 저장 = 직접 전투 재시작 지점, 5.3)
- 난수 상태 저장으로 자동 정산 결과는 재로드해도 동일

### 3.5 플레이어 설정

세이브(캠페인 진행)와 분리된 설정 파일 하나. 모든 캠페인에 공통이고, 세이브 스키마 버전과 무관하다.

| 분류 | 항목 (전투 프로토타입 근거) |
|---|---|
| 조작 | 패드 배치 (기본 = 트리거 스로틀, Q8), 키 재배치 (Input System 리바인딩 결과 JSON), 순항 복귀 켜기/끄기 (Q2) |
| 전투 보조 | 링 메뉴 슬로모션 켜기/끄기·배율 (Q5, 기본 켜기), 레이더 표시 방식 (Q3) |
| 화면·소리 | 해상도, 음량, 언어 |

- 저장은 Infra, 포맷은 JSON (작고 사람이 고칠 수 있어야 함 — 세이브와 달리 로드 경로가 JSON)
- 난이도 모디파이어(4.7)는 설정이 아니라 캠페인 세이브에 속한다

## 4. 전략 레이어

### 4.1 헥스 좌표

- pointy-top
- 저장은 축 좌표(q, r), 연산은 큐브 좌표로 변환
- 거리·인접·직선(편대 비행 경로)·범위(이동 가능 칸, 탐지, 미확인 접촉, 대공 위협, 급유 범위)를 정수 연산으로 처리
- 직선은 경계에서 한쪽으로 치우치게 반올림해 결정론을 지킨다 (부동소수 동률 금지)

### 4.2 맵 데이터

- 헥스별 지형, 소속 구역을 가진 평면 배열
- 구역, 고유 거점, 자원 타일(종류·초기 소유·등급), 세력 배치 후보, 초기 부대는 별도 목록
- Core는 맵 데이터만 알고 렌더링 방식은 모름

### 4.3 커스텀 헥스 맵 에디터

| 레이어 | 내용 |
|---|---|
| 지형 | 평지·산악·해상·해안·사막 등 페인팅 |
| 구역 | 경계와 개방 순서 |
| 고유 거점 | 위치, 종류, 초기 등급 |
| 자원 타일 | 위치, 종류(유전·광산·도시), 초기 소유·등급 |
| 배치 후보 | 세력별 시작 위치 후보군 (리플레이 배치 변화용) |
| 초기 부대 | 세력별 초기 부대·지상군 |

- 결과물은 맵 데이터 에셋 1개
- 검증: 고유 거점 ID 존재, 구역 연결성, 배치 후보 수 등 (3.1과 동일 파이프라인)

### 4.4 전략 맵 렌더링

- 헥스별 오브젝트를 두지 않고 청크 단위 병합 메시로 지형 렌더링
- 오버레이(영역 경계, 이동 가능 칸, 시야 안개, 대공 위협 범위, 급유 범위)는 셰이더 입력 텍스처로 처리 → 반경·안개가 바뀌어도 메시 재생성 불필요
- 유닛 표식(거점·자원 타일·비행 편대·적 부대·미확인 접촉 "?"·급유기)은 오버레이와 분리된 스프라이트 층. 이동 재생은 이 층만 움직인다

### 4.5 이동과 시야

- 지상군·적 부대 이동: 헥스 A*, 지형별 이동 비용. 여러 턴 이동은 경로 저장 후 턴마다 진행
- 편대 비행: 경로 탐색 없이 헥스 직선. 칸마다 연료·이동력 1. 지형 비용 없음
- 시야: 세력별 가시 헥스 집합 (거점 영역 + 레이더 반경 + 비행 편대 주변 + 지상군·자원 타일 주변 + 정찰 결과 유지 턴)
- **미확인 접촉**: 가시 집합 밖이지만 거점 시야 + 접촉 거리 안의 적 부대를 "?"로 낸다. 정체·전력은 넘기지 않고 위치와 지난 위치만 넘긴다. 레이더가 없는 거점이 잡은 접촉은 위치 오차(2.6의 해시로 고정). 접촉은 상태가 아니라 조회 결과
- 세력별 **마지막 목격 정보**: 한 번 본 부대 위치를 기억하되 시간에 따라 신뢰도 감소. 목격 갱신은 적 턴 직전과 직후 두 번 (적이 거쳐 간 칸에서 본 것도 남긴다)

### 4.6 적 전략 AI

| 층 | 역할 | 데이터 |
|---|---|---|
| 태세 (상위) | 확장·공세·방어·재정비 중 하나를 수 턴 유지, 전환 조건 충족 시 변경 | 세력별 전환 문턱값 (xlsx) |
| 행동 선택 (하위) | 현재 태세에서 허용된 행동 후보를 점수화해 선택 | 태세별·성향별 가중치 (xlsx) |
| 공통 평가 | 영향력 맵(헥스별 아군·적 전력 분포, 위협도, 가치) 턴마다 계산 | — |
| 공세 조율 (세력) | 공세 태세일 때 여러 부대에 서로 다른 목표를 같은 시기에 배정 → 플레이어가 여러 방향의 위협을 동시에 받게 함 (기획서 9장) | 동시 공세 수, 목표 간 최소 거리 |

- AI는 시야 규칙을 준수. 정보가 오래된 지역일수록 정찰 행동 점수 상승
- 목표 후보: 아군 거점, 자원 타일(점령), 탐지한 급유기, 맞닿을 수 있는 비행 편대. 적 거점 주변에는 호위 부대를 남기는 행동이 있다 (기획서 9장 거점 방어 구성)
- Core 내 무상태 서비스 → 헤드리스 시뮬레이션에서 그대로 동작 (세력끼리만 N턴 돌리기)
- 태세는 정찰로 탐지한 세력에 한해 전략 맵에 표시

### 4.7 난이도 모디파이어

개별 적용 가능한 모디파이어, 난이도 프리셋은 조합:
- AI 판단 품질 (가중치·예측 깊이)
- AI 자원 보너스
- 전투 난이도
- 직접 전투 재시작 허용 (5.3 참조)
- 적 선공 교전의 직접 플레이 허용 (5.3 참조)

## 5. 출격 인터페이스 — 교전 계약

### 5.1 계약

직접 플레이와 자동 정산은 같은 입출력을 쓴다. **계약의 단위는 교전 1건**이다. 기획서 v0.3에서 다턴 비행을 채택하면서 "출격 1회 = 전투 1회"가 "이륙 1회 = 교전 0~N회(턴당 최대 1회)"가 됐다. 이륙·비행·착륙·연료는 전부 Core의 일이고, Combat은 교전 한 판만 안다.

```csharp
// Game.Contracts
public sealed record SortieContext(          // 교전 1건
    SortieId Id,
    MissionType Mission,          // 부대 공격, 거점 폭격, 자원 타일 폭격, 요격, 정찰, 호위, 보급선 차단, 구출
    EngagementInitiator Initiator,// Player(명령한 칸에 도착) / Enemy(적 선공·거점 자동 요격)
    TerrainType Terrain,
    int EnemyTier,                // 적 단계 (전력 + 진행 단계)
    EnemyForceSnapshot Enemy,     // 지금 월드의 적 구성 (앞 교전의 피해는 월드에 이미 반영됨 — 별도 보정치 없음)
    BossId? Boss,
    RivalId? RivalCandidate,      // 난입 가능 라이벌 + 확률
    SquadronSnapshot Squadron,    // 이번에 나는 기체만: 파츠·무장·현재 손상(앞 교전 포함), 파일럿(능력치·피로·숙련 기종)
    bool IsOverEnemyTerritory,    // 탈출 시 포로 판정용
    uint Seed);

public sealed record SortieResult(
    SortieId Id,
    float DestructionRate,        // 목표 파괴율 → 전략 효과
    IReadOnlyList<AircraftOutcome> Aircraft,   // 손상, 격추 여부, 전경 시간
    IReadOnlyList<PilotOutcome> Pilots,        // 경험치, 탈출
    IReadOnlyList<KillRecord> Kills,           // 현상금, 적 에이스 격추
    IReadOnlyList<LootId> Loot,                // 역설계 대상
    ExitReason Exit);             // 완료, 이탈 지점 철수, 전멸
```

**v0.3 대비 바뀐 점**

| 항목 | v0.3 | v0.4 | 이유 |
|---|---|---|---|
| 단위 | 출격 1건 | 교전 1건 | 다턴 비행 (기획서 3장) |
| 앞 결과 반영 | `EnemyForceSnapshot`에 "앞 출격 보정치" 적용 (겹침 보정) | 앞 교전의 피해가 월드 상태에 바로 반영되고, 스냅샷은 지금 월드를 그대로 읽음 | 겹침 보정 삭제 (기획서 3장). 턴 상태의 "대기 보정치"도 없어짐 |
| 편대 | 출격 가능한 기체 전부 | 이륙한 기체 중 아직 날 수 있는 기체 | 한 이륙에서 여러 번 교전하면 손상이 누적됨 |
| 발생 경위 | 플레이어 출격만 | `Initiator` 추가 | 적 선공·거점 자동 요격도 같은 계약 |
| 비용 | 출격마다 | 이륙 때 한 번 (Core) | 교전 컨텍스트에는 비용이 없다 |

**Combat 밖에 남는 것**: 연료·드롭탱크(교전 시작 때 Core가 투하 처리), 맵 위치, 급유기, 교전 후 이동. Combat에 필요하면 연출용 플래그만 추가한다 (예: 드롭탱크 투하 연출).

### 5.2 흐름

1. 교전이 생긴다
   - 플레이어 턴: 비행 명령의 도착 칸이 적 부대·적 거점·적 자원 타일 (편대는 턴당 1회만 교전)
   - 적 턴: 적 부대가 비행 편대와 맞닿음(적 선공), 또는 편대가 주둔한 거점을 공격(자동 요격)
2. Core 턴 처리기가 `SortieContext` 1건을 만들고 교전 대기 상태로 멈춘다 (2.5). 드롭탱크 투하 등 교전 시작 처리는 이때 Core가 한다
3. App이 직접/자동을 정한다 (5.3 정책 + 플레이어 선택)
   - 자동 정산 → Core 내부 리졸버가 즉시 `SortieResult` 생성
   - 직접 플레이 → App이 필요 에셋 사전 로드 후 Combat 씬을 컨텍스트와 함께 로드 → 종료 시 결과 반환 → Core에 제출
4. Core가 결과 적용 (파괴율 효과, 손상·격추·잔해 회수·포로, 경험치, 보상, 날 수 있는 기체가 없으면 비행 종료) → 멈춘 지점부터 이어 감 (플레이어 턴이면 명령 대기, 적 턴이면 남은 걸음)

**책임 한계**: Combat은 사실만 보고한다. 경손상(대기 시간 비례), 포로 판정, 보상, 잔해 회수, 전략 효과 계산은 모두 Core. 규칙이 한 곳에 모이므로 직접·자동 간 규칙 차이가 생길 수 없다.

### 5.3 정책

| 항목 | 결정 |
|---|---|
| 직접/자동 선택 | 교전마다. 보스·스토리 교전은 직접 필수 |
| 적 선공 교전 | 계약·상태 머신은 직접 플레이를 지원한다 (적 턴 커서로 멈춤·재개). 실제 허용 여부는 기획서 12장 결정에 따라 정책 값 하나로 켜고 끈다. 끄면 자동 정산만 |
| 거점 자동 요격 | 자동 정산 (기획서 3장). 요격 미션(플레이어 출격)과 별개 |
| 직접 전투 재시작 | 난이도 모디파이어로 허용 시 교전 직전 스냅샷(자동 저장)으로 복귀 |
| 전투 도중 자동 정산 전환 | 불가 |
| 교전 통계 기록 | 교전마다 발생 경위·미션·직접/자동 선택·소요 시간을 플레이 로그에 남긴다 → 기획서 12장 "다턴 비행의 교전 빈도와 직접 플레이 비중" 판단 자료 |

### 5.4 자동 정산 리졸버 — 추상 교전 라운드

- 적 구성을 청크 수에 맞춰 교전 그룹(공중·지상·대공)으로 분할
- 라운드마다 편대 기체 1기가 전면에서 교전. 역할 상성, 파일럿 능력치·숙련 기종, 무장, 손상 상태로 피해 교환
- 손상이 커지면 다음 기체로 교대 → 기체별 전경 시간(라운드 수)이 자연스럽게 산출
- **최소 교전**: 교대 기준을 넘은 기체만 남아도 가장 덜 손상된 기체가 최소 1라운드는 싸운 뒤 철수 (기획서 3장, 전략 프로토타입 S7 결함)
- 라이벌 난입은 라운드 중간 이벤트, 보스는 마지막 라운드 그룹
- "직접 대비 약간 불리"는 리졸버 전체 보정 계수 하나로 조정 (전략 프로토타입 0.85에서 결과 카드만 보고 납득 가능)
- 결과는 직접 전투와 동일한 `SortieResult`
- **확장 지점**: 직접 플레이 로그(미션·적 단계별 실제 성과)를 기록해 보정 계수를 플레이어 실력 기준으로 맞추는 로그 보정 (후속)

### 6.1 구성 요소

| 세로 카메라 | 플레이어 세로 위치를 0.2초 감쇠로 추적 (Q3 "부드럽게") |
| 기체 전환 | 편대 전체 3D 모델 사전 로드. 전환 시 전경 기체 교체 + 무방비 타이머, 빠지는 기체는 배경 레이어로 교대 연출 |
| 배경 레이어 편대 | 축소 스케일·느린 스크롤·대기 원근 셰이더. 판정 없음, 미리 만든 비행 경로 + 가짜 탄 이펙트 |
| 결과 기록기 | 전투 이벤트(격추, 피해, 기체별 전경 시간, 획득물) 누적 → 종료 시 `SortieResult` 생성 |

### 6.2 DOTS 사용 범위 — 가벼운 하이브리드 (Entities 미사용)

| 대상 | 처리 |
|---|---|
| 플레이어 기체, 보스 | GameObject |
| 탄 (아군·적) | NativeArray 구조체 데이터 + Burst Job 이동·충돌, 인스턴싱 렌더링 (RenderMeshInstanced 또는 BRG) |
| 잡몹 | GameObject + 풀링, 이동 패턴은 TransformAccessArray Job |

- 충돌은 물리 엔진 미사용. 매 프레임 플레이어·보스·잡몹 히트박스(원·박스)를 NativeArray에 복사해 탄 Job에서 일괄 판정
- 탄·폭탄의 지형 충돌은 지형 높이 곡선(6.7)을 NativeArray로 넘겨 같은 Job에서 판정 (프로토타입에서 검증된 방식)
- 탄 렌더링은 `Graphics.RenderMeshInstanced`로 시작. BRG는 프로파일링에서 병목이 확인될 때만
- Entities를 쓰지 않는 이유: 서브씬 베이킹과 GameObject 동기화 비용. 예상 규모(동시 탄 수백 단위)에서는 Jobs/Burst로 충분
- 탄·잡몹 데이터를 처음부터 구조체 배열로 설계해 Entities 이전 경로 확보

### 6.3 청크

- 저작 단위: **프리팹** (지형 높이 곡선·배경·앵커). 판정의 원본은 높이 곡선이고 지형 메시는 곡선에서 생성한다 (6.7)
- 환경(조명·하늘·안개)은 **지형별 환경 프로필** (URP 볼륨 프로필 + 하늘 설정)로 분리
- 청크 메타데이터: 지형·미션·난이도 태그, 진입·이탈 규격(경계의 바닥·천장 높이), **선회 속성** (6.8)
- 청크 경계마다 이탈 지점, 보스 직전 필수
- 일반 스테이지: 생성기가 조건에 맞는 청크를 이어 붙임 / 스토리·고유 거점: 같은 청크의 고정 시퀀스

### 6.4 적 등장과 지상 목표

| 요소 | 저작 위치 |
|---|---|
| 등장 위치 | 청크의 앵커 (공중·지상) |
| 이동 궤적 | 스플라인 에셋 라이브러리 (재사용) |
| 웨이브 구성·타이밍 | xlsx, 적 단계별 정의. 궤적은 ID로 참조 |
| 지상 목표·대공 배치 | xlsx, 지형 × 미션 × 적 단계별 정의, 청크 지상 앵커에 배치 |

청크는 여러 적 단계·미션에서 재사용되므로 적을 청크에 굽지 않는다.

### 6.5 보스

- 부위(파츠)별 체력과 파괴 시 패턴 변화를 가진 GameObject 계층
- 보스별 개별 Addressables 그룹
- **고정형 보스(지상 요새)의 본체는 지형으로 처리**: 본체 외곽을 지형 높이 곡선(6.7)에 합쳐 충돌·탄 차단·폭탄 폭발을 지형 코드로 공유한다. 부위(포탑·코어)만 히트박스를 가진다 (전투 프로토타입 6단계)
- 고정형 보스전은 선회 구역(6.8) 안에서 진행. 구역 길이 160m 전후, 자동 선회 1.2초 (Q6)

### 6.6 좌표계와 진행 방향

| 대상 | 좌표계 |
|---|---|
| 적 기체·잡몹, 지상 목표, **적 탄**, **폭탄**, 지형 | 지면 좌표 (스크롤 원점 기준 월드 x) |
| 플레이어 기체, 기관포 탄 | 화면 좌표 (카메라 기준) |

- 근거: 적 탄만 화면 좌표일 때 가감속하면 탄이 따로 노는 것처럼 보였다 (전투 프로토타입 3단계). 지면 좌표로 옮기자 해소
- 공중 적의 탄은 발사 기체 속도를 계승한다. 적 예측 사격은 플레이어의 대지 속도 기준 (정확도는 적 정의의 0~1 값)
- 폭탄은 투하 시 기체의 대지 속도를 계승하되 **0 이상으로 제한** (화면 내 뒤로 이동은 후진이 아님)
- 탄 Job은 두 좌표계 배열을 따로 둔다. 판정 직전에 같은 공간(지면 좌표)으로 변환
- **진행 방향 반전(선회)**: 스크롤 속도는 부호를 가진 값이다. 선회 = 속도가 0을 지나 반대 부호로 (기본 1.2초, 조작 불능·무적·적 미등장·전경 시간 정지). 지면 좌표계의 모든 계산은 방향에 무관해야 한다 ("앞 = +x" 가정 금지)
- 청크 로드·해제: 일반 구간은 지나간 청크를 해제하지만, 선회 구역 청크는 구역을 벗어날 때까지 유지

### 6.7 지형 높이 곡선

- 청크마다 지면 x에 대한 **바닥·천장 높이 배열**(고정 간격 샘플)을 가진다. 저작은 청크 프리팹의 2D 제어점, 에디터 임포트 시 배열로 굽는다
- 같은 곡선을 판정(기체·탄·폭탄), 지형 메시 생성, **전방 지형 예고**(레이더·경고, 기획서 7장, 전투 Q9)가 읽는다 → 보이는 것과 맞는 것이 어긋나지 않는다
- 지형 충돌 피해는 큰 값(즉사 또는 큰 피해)으로 정의하되, 그만큼 예고가 전제다 (Q9). 수치는 xlsx
- **검증기 (3.1 파이프라인)**: 최고 스크롤 속도에서 반응 시간 안에 피할 수 없는 경사(단위 거리당 높이 변화 한도), 최소 통로 높이 미만 구간을 빌드 단계에서 거부한다 (Q9 "고속 중 갑자기 나타난 급경사")

### 6.8 기체·청크의 전투 속성

| 속성 | 위치 | 내용 |
|---|---|---|
| 가로 입력 배율 | 기체 정의 (xlsx) | 가속 폭·감속 폭 배율. 역할별 기동성 차이 (프로토타입: 제공기 가속 ×1.3, 폭격기 가속 ×0.6·감속 ×0.8) |
| 선회 속성 | 청크 메타데이터 | 없음 / 자동 선회 구역(양 끝) / 임의 선회 허용. 일반 진행 구간은 선회 없음, 선회 구역·보스전은 임의 선회 허용 (Q7) |
| 기체 전환 무방비 | 전투 공통 정의 (xlsx) | 발사 불가 + 세로 이동 ×0.5, 0.5초, 피격 무적 없음 (Q4) |

## 7. 렌더링·아트 파이프라인

### 7.1 방향

| 항목 | 결정 |
|---|---|
| 스타일 | 툰(셀) 셰이딩 + 외곽선 |
| 텍스처 | 공유 팔레트 텍스처 + 기체별 디칼(마크·도장) |
| 외형 반영 | 하드포인트 무장만 (부품 개조는 수치로만) |

### 7.2 셰이더

- **툰**: URP 커스텀 셰이더, 램프 텍스처 기반 2~3단 명암. 전투 씬은 고정 키 라이트 1개로 단순화
- **외곽선**: 기체·잡몹·보스는 인버티드 헐. 오브젝트별 두께 조절, 배경 레이어 편대는 얇게 또는 끔. 탄·원경은 외곽선 없음
- **세력 도장**: 팔레트 텍스처를 행 단위 세력 색 세트로 구성, 셰이더에서 행 오프셋 교체 → 기체 모델 하나로 전 세력 표현
- **디칼**: 디칼 프로젝터 미사용. 메시 UV2에 마크 위치, 디칼 아틀라스를 셰이더에서 합성 (에이스 마크·부대 문장은 아틀라스 칸 교체)
- **손상**: 모델 파손 상태 없음. 연기·불꽃 파티클 + 셰이더 그을음 마스크
- 커스텀 패스는 Unity 6 URP 렌더 그래프 API 기준

### 7.3 하드포인트

- 블렌더 Empty를 `HP_L1`, `HP_R1`, `HP_C` 등으로 배치 → 임포트 시 트랜스폼
- 무장 모델은 전 기종 공용, 장착 규칙은 xlsx

### 7.4 블렌더 작업 규칙

| 규칙 | 내용 |
|---|---|
| 단위 | 1 unit = 1m, 내보내기 전 트랜스폼 적용 |
| 축 | 기체 앞쪽 방향 통일, Unity 임포트 축 변환 설정 고정 |
| 폴리곤 예산 | 소형 기체 기준 수천 폴리곤 내외 (확정은 프로토타입 후). 직교 카메라라 LOD 불필요 |
| 머티리얼 | 기체당 1개 (팔레트), 디칼은 UV2 |
| 명명 | 파일명 = 기체 ID (예: `AC_F16.fbx`), 루트 오브젝트 = ID, 소켓 `HP_`·`MZ_`·`FX_`·`PT_` (2.10.3) |
| 위치 | 원본 `.blend`는 저장소 밖 원본 루트의 `Blender/<ID>/` (2.7), 내보낸 FBX는 `Assets/_Game/Content/<분류>/<ID>/` |

## 8. 리소스·빌드

### 8.1 버전 관리

- Git + LFS
- `.gitattributes`: FBX, 텍스처, 오디오, `.xlsx` → LFS
- `.blend` 등 제작 원본은 Git에 넣지 않는다 (저장소 밖 동기화 폴더, 2.7). LFS에는 내보낸 결과만 쌓이므로 용량 증가가 완만하다. GitHub LFS 무료 용량을 넘으면 데이터 팩 추가를 검토
- 씬·프리팹 병합용 UnityYAMLMerge 등록
- 본 게임은 `main`에서 새 브랜치로 시작한다. 프로토타입 브랜치(`prototype/*`)와 `Assets/Prototype/`은 본 게임 브랜치로 병합하지 않는다 (프로토타입 = 버리는 코드). 남길 것은 문서(플레이테스트 기록·확정 수치)뿐

**주의사항**
- R3.Unity·MessagePack.Unity는 NuGet 쪽 핵심 라이브러리가 먼저 있어야 컴파일된다. 한 번에 넣지 말고 설치 순서를 지킨다
- MessagePipe.VContainer의 `package.json`에는 의존성이 비어 있어 코어(`com.cysharp.messagepipe`)가 자동 설치되지 않는다. 코어를 같은 태그로 반드시 함께 추가 (누락 시 `IServiceCollection` 미정의 에러 — 이 인터페이스는 코어의 `DependencyInjectionShims.cs`에 정의됨)
- UniTask가 설치되어 있으면 VContainer의 비동기 진입점 연동이 자동 활성화
- 빌드 재현성: `Packages/packages-lock.json`, NuGetForUnity의 `Assets/Packages/`와 `Assets/packages.config`를 커밋 → Jenkins 빌드가 네트워크 복원에 의존하지 않음
- NuGetForUnity 설치 위치 `Assets/Packages/`는 `Assets/_Game/`과 분리되어 폴더 구조(2.7)와 충돌하지 않음
- Core asmdef에는 MessagePack(NuGet 코어)만 참조로 추가 (`overrideReferences` + 명시 참조). R3·R3.Unity·UniTask·MessagePipe 참조는 금지 (2.1 규칙이 컴파일 단계에서 강제됨)
- 현재 manifest의 MessagePipe·MessagePipe.VContainer 항목에는 `#1.8.2` 태그가 빠져 있다 → 위 URL대로 고정

### 8.5 Unity 밖 Core 프로젝트 (`DotNet/`)

| 프로젝트 | 내용 |
|---|---|
| `Game.Core.csproj` | `netstandard2.1`, `LangVersion 9`. `Assets/_Game/Code/Core/**/*.cs`와 `Contracts/**/*.cs`를 링크로 포함 (`<Compile Include=... Link=...>`). NuGet: MessagePack 3.1.10 (Unity 쪽과 같은 버전) |

- Unity 쪽 asmdef와 이 csproj가 같은 소스를 컴파일하므로, 한쪽에서만 되는 코드(Unity API, C# 10 이상 문법)는 즉시 드러난다 — 2.1 경계가 두 번 강제됨
- 에디터를 연 채로 실행 가능: `dotnet test DotNet/Game.Core.Tests`
- Unity Test Framework의 EditMode 테스트는 Data 임포터·검증기처럼 Unity가 필요한 것에만 쓴다
