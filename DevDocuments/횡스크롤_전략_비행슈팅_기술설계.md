## 2. 전체 아키텍처

### 2.1 어셈블리

| 어셈블리 | 역할 | 의존 |
|---|---|---|
| Game.Core | 순수 C# 도메인: 월드, 헥스 맵, 거점·시설, 편대·기체·파일럿, 지상군, 세력, 경제, 턴 처리, 커맨드, 이벤트, 자동 정산 리졸버, 적 AI | 없음 (UnityEngine 미참조) |
| Game.Contracts | 레이어 간 공유 타입: 출격 컨텍스트·결과, 정적 데이터 정의 레코드, 메시지 구조체 | 없음 |
| Game.Data | ScriptableObject 저작 데이터, xlsx 임포터(에디터), 정의 레코드 변환 | Contracts |
| Game.Strategy | 전략 맵 뷰, 헥스 입력, 운영 패널 UI | Core, Contracts |
| Game.Combat | 전투 씬 전체 (기체, 탄 Job, 청크 생성, 보스, HUD, 결과 기록기) | Contracts만 |
| Game.Infra | 세이브/로드, Addressables 로딩, 입력·플랫폼 추상화, 씬 전환 | Core, Contracts |
| Game.App | 부트스트랩, 조립(composition root), 턴-전투 오케스트레이션 | 전부 |

**핵심 규칙**
- Combat은 Core를 모른다. 출격 컨텍스트를 받고 결과를 돌려주는 것만 안다 → 전투 씬 단독 테스트 가능, 전략 규칙 변경이 전투 코드에 파급되지 않음
- Core에는 R3 허용(Unity 비의존 코어 라이브러리), UniTask 금지(Unity 플레이어 루프 의존), MessagePipe 금지(DI 등록 전제를 Core에 들이지 않음). Core는 Unity 없이 테스트 러너에서 동작해야 한다

### 2.2 씬 구성

| 씬 | 로드 방식 | 내용 |
|---|---|---|
| Boot | 상주 | App, Infra, 전역 서비스, 루트 DI 스코프 |
| Strategy | 추가 로드 | 전략 맵, UI, Strategy DI 스코프 |
| Combat | 추가 로드 (Strategy와 교체) | 전투, 출격 컨텍스트를 주입받는 Combat DI 스코프 |

전략 상태는 전부 Core 메모리에 있으므로, 전투 중 Strategy 씬을 내려 메모리를 확보할 수 있다.

### 2.3 DI (VContainer)

- Boot의 루트 `LifetimeScope` 아래 Strategy·Combat을 씬별 자식 스코프로 구성
- Combat 스코프는 생성 시 `SortieContext`를 파라미터로 주입받음
- Core 서비스는 루트 스코프에 등록하되, Core 코드 자체는 VContainer를 참조하지 않음 (생성자 주입만 사용)
- MessagePipe는 MessagePipe.VContainer 통합으로 루트 스코프에 등록하고, 메시지 타입별 브로커도 루트에서 등록 → Strategy·Combat 자식 스코프에서 `IPublisher<T>` / `ISubscriber<T>` 주입 (용도는 2.4)

### 2.4 상태·이벤트 전달 (R3 / MessagePipe)

UI와 게임 사이에 오가는 정보를 세 종류로 나누고, 종류별로 도구를 정한다.

| 종류 | 예시 | 도구 | 이유 |
|---|---|---|---|
| 상태 | 체력, 선택된 타일, 자금, 신뢰도, 파일럿 피로 | R3 `ReactiveProperty` | UI가 필요한 것은 "지금의 값". 구독으로 자동 갱신 |
| 출처를 아는 사건 | HUD가 조종 중인 기체의 피격 연출 | R3 Observable (발생 대상이 노출) | 받는 쪽이 이미 대상을 알고 있으므로 대상에 직접 구독 |
| 출처를 모르는 사건 | 효과 매니저, 사운드 매니저, 전투 결과 기록기 | MessagePipe (VContainer 주입 `IPublisher<T>` / `ISubscriber<T>`) | 중앙 수신자가 "누가"를 몰라도 "무슨 일"을 받아야 함 |

**판단 규칙**: 값이면 R3, 출처를 모르는 곳에서 오는 소식이면 MessagePipe. 대부분의 흐름(상태 바인딩)은 R3가 맡고, MessagePipe는 중앙 집중 수신자라는 좁은 용도로만 쓴다.

**운영 규칙**
- Core는 MessagePipe를 참조하지 않는다. Core의 상태는 R3 `ReactiveProperty`로, 도메인 사건은 R3 Observable로 내보내고, 출처를 모르는 수신자에게 알려야 할 사건은 App 레이어가 받아 MessagePipe로 중계한다
- 메시지는 구조체로 정의한다 (전투 중 잦은 사건을 할당 없이 전달)
- 탄 충돌은 Burst Job에서 판정되므로, Job 완료 후 메인 스레드에서 판정 결과를 모아 발행한다
- 메시지 타입은 Contracts에 둔다 (Combat은 Contracts만 참조)
- 새 메시지 타입을 만들기 전에 "받는 쪽이 출처를 정말 모르는가?"를 확인한다. 안다면 R3로 충분하다

### 2.5 턴 처리

- Core의 턴 처리기는 **async 없는 동기 상태 머신**
- 단계: 운영(자유 순서 커맨드) → 출격 계획 확정 → 출격 실행(순차) → 턴 종료 → 아군 지상군 AI → 적 세력 턴 → 다음 턴
- 출격 실행 단계는 "다음 출격 컨텍스트 요청 → 결과 제출" 방식으로 외부 결과를 기다림
- 전투 씬 로드와 대기 같은 비동기 흐름은 App 레이어가 UniTask로 조율
- 상태 머신의 현재 위치(단계, 완료된 출격 인덱스, 대기 보정치)가 데이터이므로 어느 시점에서든 직렬화 가능 → "언제든 저장"의 전제

### 2.6 결정론

- 모든 무작위성은 Core 전용 시드 난수로 처리
- 같은 세이브 + 같은 커맨드 = 같은 결과 → 헤드리스 밸런싱 시뮬레이션, 버그 재현, 자동 정산 세이브 스컴 방지

### 2.7 프로젝트 폴더 구조

**원칙**
- 프로젝트 에셋은 `Assets/_Game/` 하나로 묶는다. 밑줄로 목록 최상단에 고정되고, 서드파티가 `Assets/` 바로 아래 만드는 폴더와 섞이지 않는다
- `_Game` 아래 최상위는 **용도별 7개로 고정**. 콘텐츠가 늘어나도 최상위는 늘지 않는다
- 최상위 아래 3단계 이내를 목표로 한다
- 여러 파일로 이뤄진 콘텐츠(기체·보스 등)는 **ID 폴더 하나에 모은다** (모델·프리팹·디칼을 함께)
- Unity가 직접 다룰 필요 없는 원본(`.blend`, `.xlsx`)은 `Assets` 밖에 둔다

**저장소 루트**

```
<repo>/
├─ Assets/
├─ Packages/
├─ ProjectSettings/
└─ SourceAssets/                 Unity 임포트 대상 아님 (LFS)
   ├─ Blender/                   .blend 원본 (기체 ID별)
   └─ Tables/                    .xlsx 원본 + 임포트 시 생성되는 JSON 텍스트 스냅샷
```

`.blend`가 Assets 안에 있으면 Unity가 블렌더를 호출해 임포트하려 하므로 블렌더가 없는 빌드 머신에서 문제가 된다. 블렌더에서 FBX로 내보낸 결과만 `Assets`에 둔다.

**Assets**

```
Assets/_Game/
├─ Code/                         어셈블리 = 폴더 (asmdef 위치가 곧 경계)
│  ├─ Core/  Contracts/  Data/  Strategy/  Combat/  Infra/  App/
│  ├─ Editor/                    임포터, 맵 에디터, 검증 도구 (에디터 전용 asmdef)
│  └─ Tests/                     EditMode / PlayMode
├─ Content/                      게임에 등장하는 것 (Addressables 그룹과 1:1)
│  ├─ Aircraft/                  AC_F16/ … (FBX·프리팹·디칼을 기체 ID 폴더에)
│  ├─ Weapons/
│  ├─ Enemies/
│  ├─ Bosses/                    BOSS_xxx/ …
│  ├─ Chunks/                    Desert/ Mountain/ Sea/ … (지형별)
│  ├─ Environment/               지형별 환경 프로필 (볼륨·하늘)
│  ├─ Strategy/                  전략 맵 타일·아이콘
│  └─ UI/
├─ Data/                         표와 도구에서 오는 것
│  ├─ Generated/                 xlsx 임포터 산출물 (직접 수정 금지)
│  ├─ Authored/                  에셋 연결 SO, 궤적 스플라인
│  └─ Maps/                      맵 에디터 산출물
├─ Rendering/                    툰 셰이더, 팔레트, 램프, 디칼 아틀라스, 공용 머티리얼·파티클 자원
├─ Audio/
├─ Scenes/                       Boot / Strategy / Combat / Sandbox
└─ Settings/                     URP / Input / Addressables / Localization
```

**폴더별 결정 근거**

| 폴더 | 근거 |
|---|---|
| `Code` | `Scripts`는 Unity가 특별한 의미를 두지 않는 관례적 이름으로, 게임오브젝트에 붙이는 MonoBehaviour라는 인상이 강하다. 이 폴더의 가장 큰 덩어리인 Core·Contracts는 Unity 비의존 순수 C# 라이브러리이고, asmdef 정의·에디터 도구·테스트 어셈블리까지 함께 담기므로 "코드베이스 전체"라는 의미로 `Code`로 명명 |
| `Content` | 하위 폴더가 Addressables 그룹과 1:1 대응 → 그룹 관리가 곧 폴더 관리. ID 폴더 묶음은 "파일명 = 기체 ID" 규칙(7.4)과 일치 |
| `Data/Generated` | 임포터가 덮어쓰는 산출물을 사람이 만드는 SO와 분리해 수정 금지 영역을 명확히 하고, 검증 도구의 대상 범위를 한정 |
| `Rendering` | 셰이더·팔레트는 특정 콘텐츠가 아니라 전 콘텐츠의 공유 기반. 특히 팔레트 행 교체로 세력 도장을 바꾸므로 기체 폴더에 두면 안 됨 |
| `Scenes/Sandbox` | Combat이 Core를 모르는 구조를 활용한 전투 단독 테스트 씬, 셰이더 실험 씬 |

**콘텐츠 폴더 예시**

```
Content/Aircraft/AC_F16/
├─ AC_F16.fbx
├─ AC_F16.prefab
└─ AC_F16_Decal.png              (디칼 아틀라스에 합쳐지기 전 원본이 필요한 경우)
```

## 3. 데이터 설계

### 3.1 정적 데이터 파이프라인

| 단계 | 내용 |
|---|---|
| 저작 | 수치·표 데이터는 로컬 Excel(.xlsx, `SourceAssets/Tables/`에 커밋). 에셋 연결은 ScriptableObject (`Data/Authored/`) |
| 연결 키 | 문자열 ID (예: `AC_F16`, `FAC_HANGAR`). 시트 행과 SO가 같은 ID로 짝을 이룸 |
| 에셋 참조 | SO에 Addressables `AssetReference`. Core와 시트는 에셋을 모르고 ID만 다룸 |
| 임포트 | 에디터 전용 xlsx 리더로 읽어 정의 데이터 에셋 생성·갱신 (`Data/Generated/`) |
| diff 보완 | 임포트 시 시트 내용을 텍스트(JSON)로도 내보내 함께 커밋 → 밸런스 변경 이력 비교 |
| 검증 | ID 참조 누락, 값 범위, 열거형 오타, SO 짝 누락 검사. 실패 시 빌드 차단 |
| 런타임 | Data 레이어가 시트 데이터 + SO를 Contracts의 불변 정의 레코드로 변환 → 정의 레지스트리로 Core에 주입 |

**xlsx 시트 구성 (예정)**
기체, 부품, 무장, 하드포인트 장착 규칙, 시설(등급별 효과), 거점 등급표, 지상군, 미션, 적 단계, 웨이브, 지상 목표 배치, 세력(AI 가중치·태세 문턱값), 로컬라이제이션 원문

### 3.2 로컬라이제이션

- Unity Localization 패키지
- 키는 ID에서 규칙으로 파생 (예: `AC_F16.name`, `AC_F16.desc`)
- 원문은 xlsx 별도 시트에서 저작, 임포터가 String Table Collection에 반영 → 저작 위치는 xlsx 하나로 유지

### 3.3 런타임 상태

- **상태와 규칙 분리**: 월드 상태는 로직 없는 순수 데이터 클래스, 규칙은 상태를 받아 변경하는 무상태 서비스 (ECS의 컴포넌트·시스템 분리와 같은 사고방식)
- 상태 자체를 직렬화하므로 별도 세이브 DTO 불필요

### 3.4 세이브

| 구성 | 내용 |
|---|---|
| 월드 상태 | 도메인 상태 전체 (정의 데이터는 ID로만 참조) |
| 턴 상태 | 현재 단계, 출격 계획 목록, 완료된 출격 인덱스, 대기 보정치 |
| 난수 상태 | Core 난수 시드와 현재 상태 |
| 메타 | 세이브 스키마 버전, 정의 데이터 버전 해시, 플레이 시간 |

- 포맷: 개발 중 JSON, 출시 MessagePack. 같은 상태 클래스에 두 직렬화기를 붙일 수 있도록 키 명시
- 스키마 버전별 마이그레이션 단계로 업데이트 후 호환 유지
- 정의 데이터 해시 불일치 시 "밸런스 변경 후 세이브" 경고
- 저장 시점: 수동은 전투 중 제외 언제든, 자동은 턴 시작과 각 출격 종료 직후
- 난수 상태 저장으로 자동 정산 결과는 재로드해도 동일

## 4. 전략 레이어

### 4.1 헥스 좌표

- pointy-top
- 저장은 축 좌표(q, r), 연산은 큐브 좌표로 변환
- 거리·인접·직선(활주로 직선 요건)·범위(작전 반경, 탐지, 작전 지역)를 정수 연산으로 처리

### 4.2 맵 데이터

- 헥스별 지형, 소속 구역, 입지 표식(유전·산악 등)을 가진 평면 배열
- 구역, 고유 거점, 세력 배치 후보, 초기 부대는 별도 목록
- Core는 맵 데이터만 알고 렌더링 방식은 모름

### 4.3 커스텀 헥스 맵 에디터

| 레이어 | 내용 |
|---|---|
| 지형 | 평지·산악·해상·해안·사막 등 페인팅 |
| 구역 | 경계와 개방 순서 |
| 고유 거점 | 위치, 종류, 초기 등급 |
| 배치 후보 | 세력별 시작 위치 후보군 (리플레이 배치 변화용) |
| 초기 부대 | 세력별 초기 부대·지상군 |

- 결과물은 맵 데이터 에셋 1개
- 검증: 고유 거점 ID 존재, 구역 연결성, 배치 후보 수 등 (3.1과 동일 파이프라인)

### 4.4 전략 맵 렌더링

- 헥스별 오브젝트를 두지 않고 청크 단위 병합 메시로 지형 렌더링
- 오버레이(영역 경계, 작전 반경, 시야 안개, 작전 지역·겹침 표시)는 셰이더 입력 텍스처로 처리 → 반경·안개가 바뀌어도 메시 재생성 불필요

### 4.5 이동과 시야

- 지상군·적 부대 이동: 헥스 A*, 지형별 이동 비용. 여러 턴 이동은 경로 저장 후 턴마다 진행
- 시야: 세력별 가시 헥스 집합 (거점 영역 + 레이더 반경 + 정찰 결과 유지 턴)
- 세력별 **마지막 목격 정보**: 한 번 본 부대 위치를 기억하되 시간에 따라 신뢰도 감소

### 4.6 적 전략 AI

| 층 | 역할 | 데이터 |
|---|---|---|
| 태세 (상위) | 확장·공세·방어·재정비 중 하나를 수 턴 유지, 전환 조건 충족 시 변경 | 세력별 전환 문턱값 (xlsx) |
| 행동 선택 (하위) | 현재 태세에서 허용된 행동 후보를 점수화해 선택 | 태세별·성향별 가중치 (xlsx) |
| 공통 평가 | 영향력 맵(헥스별 아군·적 전력 분포, 위협도, 가치) 턴마다 계산 | — |

- AI는 시야 규칙을 준수. 정보가 오래된 지역일수록 정찰 행동 점수 상승
- Core 내 무상태 서비스 → 헤드리스 시뮬레이션에서 그대로 동작 (세력끼리만 N턴 돌리기)
- 태세는 정찰로 탐지한 세력에 한해 전략 맵에 표시

### 4.7 난이도 모디파이어

개별 적용 가능한 모디파이어, 난이도 프리셋은 조합:
- AI 판단 품질 (가중치·예측 깊이)
- AI 자원 보너스
- 전투 난이도
- 직접 전투 재시작 허용 (5.3 참조)

## 5. 출격 인터페이스

### 5.1 계약

직접 플레이와 자동 정산은 같은 입출력을 쓴다.

```csharp
// Game.Contracts
public sealed record SortieContext(
    SortieId Id,
    MissionType Mission,          // 부대 공격, 거점 폭격, 요격, 정찰, 호위, 보급선 차단, 구출
    TerrainType Terrain,
    int EnemyTier,                // 적 단계 (전력 + 진행 단계)
    EnemyForceSnapshot Enemy,     // 앞 출격 보정치가 이미 반영된 적 구성
    BossId? Boss,
    RivalId? RivalCandidate,      // 난입 가능 라이벌 + 확률
    SquadronSnapshot Squadron,    // 기체(파츠·무장·손상), 파일럿(능력치·피로·숙련 기종)
    bool IsOverEnemyTerritory,    // 탈출 시 포로 판정용
    uint Seed);

public sealed record SortieResult(
    SortieId Id,
    float DestructionRate,        // 목표 파괴율 → 전략 효과
    IReadOnlyList<AircraftOutcome> Aircraft,   // 손상, 격추 여부, 전경 시간
    IReadOnlyList<PilotOutcome> Pilots,        // 경험치, 탈출
    IReadOnlyList<KillRecord> Kills,           // 현상금, 적 에이스 격추
    IReadOnlyList<LootId> Loot,                // 역설계 대상
    ExitReason Exit);             // 완료, 이탈 지점 철수, 전멸
```

### 5.2 흐름

1. Core 턴 처리기가 출격 순서대로 `SortieContext` 1건 생성 (앞 결과의 보정치 반영, 보스는 보정 제외)
2. 자동 정산 → Core 내부 리졸버가 즉시 `SortieResult` 생성
3. 직접 플레이 → App이 필요 에셋 사전 로드 후 Combat 씬을 컨텍스트와 함께 로드 → 종료 시 결과 반환 → Core에 제출
4. Core가 결과 적용 (파괴율 효과, 손상·격추·잔해 회수·포로, 경험치, 보상) → 다음 출격

**책임 한계**: Combat은 사실만 보고한다. 경손상(대기 시간 비례), 포로 판정, 보상, 잔해 회수, 전략 효과 계산은 모두 Core. 규칙이 한 곳에 모이므로 직접·자동 간 규칙 차이가 생길 수 없다.

### 5.3 정책

| 항목 | 결정 |
|---|---|
| 직접 전투 재시작 | 난이도 모디파이어로 허용 시 출격 직전 스냅샷(자동 저장)으로 복귀 |
| 전투 도중 자동 정산 전환 | 불가 |

### 5.4 자동 정산 리졸버 — 추상 교전 라운드

- 적 구성을 청크 수에 맞춰 교전 그룹(공중·지상·대공)으로 분할
- 라운드마다 편대 기체 1기가 전면에서 교전. 역할 상성, 파일럿 능력치·숙련 기종, 무장, 손상 상태로 피해 교환
- 손상이 커지면 다음 기체로 교대 → 기체별 전경 시간(라운드 수)이 자연스럽게 산출
- 라이벌 난입은 라운드 중간 이벤트, 보스는 마지막 라운드 그룹
- "직접 대비 약간 불리"는 리졸버 전체 보정 계수 하나로 조정
- 결과는 직접 전투와 동일한 `SortieResult`
- **확장 지점**: 직접 플레이 로그(미션·적 단계별 실제 성과)를 기록해 보정 계수를 플레이어 실력 기준으로 맞추는 로그 보정 (후속)

## 6. 전투 레이어

### 6.1 구성 요소

| 요소 | 구현 |
|---|---|
| 카메라 | 직교. URP 카메라 스태킹: 원경(하늘·먼 지형)은 원근 베이스 카메라, 플레이 영역과 배경 레이어 편대는 직교 오버레이 카메라 |
| 스크롤 | 카메라·플레이 영역이 전진. 기준 속도 + 플레이어 가감속 폭 |
| 기체 전환 | 편대 전체 3D 모델 사전 로드. 전환 시 전경 기체 교체 + 무방비 타이머, 빠지는 기체는 배경 레이어로 교대 연출 |
| 배경 레이어 편대 | 축소 스케일·느린 스크롤·대기 원근 셰이더. 판정 없음, 미리 만든 비행 경로 + 가짜 탄 이펙트 |
| 결과 기록기 | 전투 이벤트(격추, 피해, 기체별 전경 시간, 획득물) 누적 → 종료 시 `SortieResult` 생성 |

### 6.2 DOTS 사용 범위 — 가벼운 하이브리드 (Entities 미사용)

| 대상 | 처리 |
|---|---|
| 플레이어 기체, 보스 | GameObject |
| 탄 (아군·적) | NativeArray 구조체 데이터 + Burst Job 이동·충돌, 인스턴싱 렌더링 (RenderMeshInstanced 또는 BRG) |
| 잡몹 | GameObject + 풀링, 이동 패턴은 TransformAccessArray Job |

- 충돌은 물리 엔진 미사용. 매 프레임 플레이어·보스·잡몹 히트박스(원·박스)를 NativeArray에 복사해 탄 Job에서 일괄 판정
- Entities를 쓰지 않는 이유: 서브씬 베이킹과 GameObject 동기화 비용. 예상 규모(동시 탄 수백 단위)에서는 Jobs/Burst로 충분
- 탄·잡몹 데이터를 처음부터 구조체 배열로 설계해 Entities 이전 경로 확보

### 6.3 청크

- 저작 단위: **프리팹** (지형·배경·앵커)
- 환경(조명·하늘·안개)은 **지형별 환경 프로필** (URP 볼륨 프로필 + 하늘 설정)로 분리
- 청크 메타데이터: 지형·미션·난이도 태그, 진입·이탈 규격
- 청크 경계마다 이탈 지점, 보스 직전 필수
- 일반 스테이지: 생성기가 조건에 맞는 청크를 이어 붙임 / 스토리·고유 거점: 같은 청크의 고정 시퀀스

### 6.4 적 등장과 지상 목표

| 요소 | 저작 위치 |
|---|---|
| 등장 위치 | 청크의 앵커 (공중·지상) |
| 이동 궤적 | 스플라인 에셋 라이브러리 (재사용) |
| 웨이브 구성·타이밍 | xlsx, 적 단계별 정의. 궤적은 ID로 참조 |
| 지상 목표·대공 배치 | xlsx, 지형 × 미션 × 적 단계별 정의, 청크 지상 앵커에 배치 |

청크는 여러 적 단계·미션에서 재사용되므로 적을 청크에 굽지 않는다.

### 6.5 보스

- 부위(파츠)별 체력과 파괴 시 패턴 변화를 가진 GameObject 계층
- 보스별 개별 Addressables 그룹

## 7. 렌더링·아트 파이프라인

### 7.1 방향

| 항목 | 결정 |
|---|---|
| 스타일 | 툰(셀) 셰이딩 + 외곽선 |
| 텍스처 | 공유 팔레트 텍스처 + 기체별 디칼(마크·도장) |
| 외형 반영 | 하드포인트 무장만 (부품 개조는 수치로만) |

### 7.2 셰이더

- **툰**: URP 커스텀 셰이더, 램프 텍스처 기반 2~3단 명암. 전투 씬은 고정 키 라이트 1개로 단순화
- **외곽선**: 기체·잡몹·보스는 인버티드 헐. 오브젝트별 두께 조절, 배경 레이어 편대는 얇게 또는 끔. 탄·원경은 외곽선 없음
- **세력 도장**: 팔레트 텍스처를 행 단위 세력 색 세트로 구성, 셰이더에서 행 오프셋 교체 → 기체 모델 하나로 전 세력 표현
- **디칼**: 디칼 프로젝터 미사용. 메시 UV2에 마크 위치, 디칼 아틀라스를 셰이더에서 합성 (에이스 마크·부대 문장은 아틀라스 칸 교체)
- **손상**: 모델 파손 상태 없음. 연기·불꽃 파티클 + 셰이더 그을음 마스크
- 커스텀 패스는 Unity 6 URP 렌더 그래프 API 기준

### 7.3 하드포인트

- 블렌더 Empty를 `HP_L1`, `HP_R1`, `HP_C` 등으로 배치 → 임포트 시 트랜스폼
- 무장 모델은 전 기종 공용, 장착 규칙은 xlsx

### 7.4 블렌더 작업 규칙

| 규칙 | 내용 |
|---|---|
| 단위 | 1 unit = 1m, 내보내기 전 트랜스폼 적용 |
| 축 | 기체 앞쪽 방향 통일, Unity 임포트 축 변환 설정 고정 |
| 폴리곤 예산 | 소형 기체 기준 수천 폴리곤 내외 (확정은 프로토타입 후). 직교 카메라라 LOD 불필요 |
| 머티리얼 | 기체당 1개 (팔레트), 디칼은 UV2 |
| 명명 | 파일명 = 기체 ID (예: `AC_F16.fbx`), 소켓은 `HP_` 접두사 |
| 위치 | 원본 `.blend`는 `SourceAssets/Blender/`, 내보낸 FBX는 `Assets/_Game/Content/<분류>/<ID>/` |

## 8. 리소스·빌드

### 8.1 버전 관리

- Git + LFS
- `.gitattributes`: FBX, 텍스처, 오디오, `.blend`, `.xlsx` → LFS
- 씬·프리팹 병합용 UnityYAMLMerge 등록

### 8.2 Addressables 그룹

| 그룹 | 내용 | 로드 시점 |
|---|---|---|
| 공용 | UI, 폰트, 공용 셰이더·팔레트, 공용 무장 | 부팅 |
| 전략 | 전략 맵 렌더링, 아이콘 | 전략 씬 진입 |
| 기체 | 기체별 모델·프리팹 (기체 ID 라벨) | 출격 시 편대 구성분만 |
| 청크 | 지형별 청크 묶음 + 환경 프로필 | 출격 시 해당 지형만 |
| 적 | 적 기체·잡몹, 궤적 스플라인 | 출격 시 웨이브 표가 요구하는 것만 |
| 보스 | 보스별 개별 | 보스 출격 시 |
| 로컬라이제이션 | 언어별 | 언어 선택 시 |

- 출격 컨텍스트가 필요 에셋 목록을 모두 알고 있으므로 전투 씬 로드 전 사전 로드 → 전투 중 로딩 없음
- PC 선행 단계는 원격 카탈로그 없이 로컬 번들. 패치 전략은 콘솔 대응 시점에 재검토

### 8.3 빌드 자동화

기존 로컬 빌드 머신(Hyper-V, Jenkins 등) 유지. 콘솔 SDK도 추후 같은 머신에 설치.

| 3. EditMode 테스트 | Core 규칙 단위 테스트 + 헤드리스 시뮬레이션 스모크 (세력 AI끼리 N턴, 예외·파산 여부) |

**주의사항**
- R3.Unity·MessagePack.Unity는 NuGet 쪽 핵심 라이브러리가 먼저 있어야 컴파일된다. 한 번에 넣지 말고 설치 순서를 지킨다
- MessagePipe.VContainer의 `package.json`에는 의존성이 비어 있어 코어(`com.cysharp.messagepipe`)가 자동 설치되지 않는다. 코어를 같은 태그로 반드시 함께 추가 (누락 시 `IServiceCollection` 미정의 에러 — 이 인터페이스는 코어의 `DependencyInjectionShims.cs`에 정의됨)
- UniTask가 설치되어 있으면 VContainer의 비동기 진입점 연동이 자동 활성화
- 빌드 재현성: `Packages/packages-lock.json`, NuGetForUnity의 `Assets/Packages/`와 `Assets/packages.config`를 커밋 → Jenkins 빌드가 네트워크 복원에 의존하지 않음
- NuGetForUnity 설치 위치 `Assets/Packages/`는 `Assets/_Game/`과 분리되어 폴더 구조(2.7)와 충돌하지 않음
- Core asmdef에는 R3(NuGet 코어)만 참조로 추가. R3.Unity·UniTask·MessagePipe 참조는 금지 (2.1 규칙이 컴파일 단계에서 강제됨)
